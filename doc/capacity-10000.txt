一万在线用户容量与统计部署说明
验证日期：2026-10-27，Asia/Shanghai

目标与边界
“一万用户”必须同时约束每人连接数和总带宽。本次完成代码优化、现有链路统计修复和一万条回环连接验证；
这不等于已验收一万真实用户持续传输，也不等于十万连接或十 Gbps 已达标。

用户数    每人连接    逻辑连接    每个 TCP 代理跳的套接字    双向32KiB复制缓冲预算
10000     1           10000       20000                     625 MiB
10000     5           50000       100000                    3125 MiB
10000     10          100000      200000                    6250 MiB
缓冲预算不含内核 socket、goroutine、TLS、协议状态、用户态网络栈、监控和控制面。
回环小包测试的 RSS 不能代替所有缓冲均被填充的持续传输内存预算。
10000人平均100Kbps需要1Gbps；平均1Mbps需要10Gbps。带宽是整个入口/出口链路共同的约束。

现场结果
- 香港：16 CPU / 16 GiB；约2.38万 ESTABLISHED 套接字，主要由 sing-box 持有。
  sing-box约2.6 GiB、1.77核；Node Manager约1.5 GiB、0.98核；面板Java约0.54 GiB且CPU很低。
- 深圳：8 CPU / 8 GiB；约2.07万 ESTABLISHED 套接字。
  原VLESS GOST约1.34 GiB、0.93核。采样公网/专线流量约300Mbps量级。
- 两台均有可用内存且 memory PSI 为0，不能把文件缓存或单进程100%理解为整机耗尽。
- Python采样证实连接详情接口反复解析大JSON并扫描用户列表。
  文件版本快照与索引优化后，20次相同查询3.65秒降至0.26秒，返回JSON摘要相同。
  上线后一次采样Python RSS约215MiB、CPU约0.67核；不同时间业务负载会变化，非严格A/B压测。
- 受限回环验证：10000 TCP连接，小包逐条回显，0错误，建立/检查约9.7秒，
  转发进程RSS约354MiB，FD20006。测试进程组限制CPU1核、MemoryMax2GiB。
  测试已结束，监听端口和进程已回收；没有向生产用户发压测流量。

当前硬约束
1. 深圳源端口范围32768..60999，共28232个。连接都发往同一出口IP/端口时，不能仅靠提高FD承载5万/10万连接。
   实际还要留出TIME_WAIT、重连和其他连接的余量；每条源IP通道按70%使用率约19762连接做预算。
   不建议通过缩短TIME_WAIT、丢弃conntrack或强杀健康连接“解决”容量问题。
2. 一万用户每人5~10连接时，现有8GiB入口的内存、源端口和CPU没有充分余量。
   当前没有万人真实流量压测证据，不能宣称现有单入口/单出口已经可稳定承载此目标。
3. 入口只转发加密TCP，不能按住宅业务用户识别身份。Flux服务名中的用户是面板配额所有者，
   它不自动等于Node Manager的每个终端用户。终端用户限额需要在认证后的出口执行。
4. 当前面板统计只有少量服务每5秒上报；SQLite不是本次CPU热点。不要为这个故障直接覆盖为MySQL版后端。
5. BBR不能消除Python全量解析、应用缓冲和源端口上限。香港已有BBR/fq，深圳保持原内核算法未修改。

已实施的架构调整
- 控制连接与计量分离：独立转发器以 -standalone -report-config <节点凭据文件> 运行。
  复用已有节点身份，只上报流量，不连接第二条管理WebSocket，也不上报不完整配置触发控制面清理。
- 独立转发器必须使用对应的 forwardId_userId_userTunnelId_tcp 服务名；不要使用任意名字后期待面板自动认领。
- 流量上报失败保留待确认字节；没有新流量时也重试。观察器故障不再通过continue冻结计量。
  成功确认使用原子减法，保留HTTP请求期间的新字节。
  现有后端协议仍缺少端到端幂等报告ID，网络“服务端已提交但响应丢失”时不能保证严格exactly-once；
  不要把本次修复描述为账务级可靠消息系统。
- TCP双向复制缓冲从2x64KiB降为2x32KiB，并复用调用者完成一个方向，减少一个goroutine。
  UDP及未知端点保留64KiB，另有65507字节报文回归。
- Node Manager连接详情使用单份按inode/mtime/ctime/size版本失效的只读快照与索引。
  修改路径仍读新字典；暂停、到期判断不缓存；文件变更解析失败时不返回旧凭据。
- 切换只影响新连接；旧转发进程保留排空。每分钟检查，只有旧进程全部连接结束且替代进程健康才停用旧单元。
  排空期间存在新旧进程同时驻留内存。旧路径已有连接在自然结束前尚未纳入新计量，不能精确补回历史缺失流量。
- 面板改为按时间戳组织自然小时，并显示本小时累计；每30秒刷新，可见性切换与卸载时停止重复轮询。
  补零占位不能覆盖真实记录，缺失快照不伪装成已测得0。
- 前端以本地Docker镜像固化，Compose覆盖指向新镜像；保留原版静态资源/代理配置的回滚镜像。
  保留生产SQLite后端、数据卷和现有WireGuard路由。

一万用户的扩容方案
推荐按用户ID固定分片，而非在一个Python进程或一个源端口池中继续堆连接。

客户端 -> 稳定用户分片映射 -> 多组入口 -> 各组WireGuard通道 -> 认证出口 -> 住宅代理
                                  |                           |
                                  +----- 聚合计量/控制API -----+

- 以4组入口/出口作为候选起步：每组2500用户，对应1.25万~2.5万逻辑连接。
  每组至少2条源IP通道或等效的目标IP/端口通道，为最高连接场景与TIME_WAIT留余量。
  WireGuard AllowedIPs、路由、源地址绑定必须成套配置，不能只往网卡加IP。
- 候选规格：每入口8~16核/16GiB，每出口16核/32GiB；实际应由目标Gbps与协议压测决定，
  这些是容量预算起点，不是性能保证。为失去一组的情况预留N+1或足够空余容量。
- 用户创建、权限、到期与住宅绑定写入持久化控制存储；连接详情用版本化读模型和分页/批量API。
  数据面不为每个数据包调用Java/Python，连接/计量聚合后再上报。
- 计量事件增加(nodeId,epoch,sequence)或报告ID，并在事务内去重后更新配额；
  跨节点只汇总各自的原始计数，不重复计费同步副本。先做协议迁移与回归，再切换账务路径。
- 每分片设置总连接、单用户连接、连接建立速率和内存预算；超预算拒绝新连接并有明确指标。
  CPU持续75%、内存70%、conntrack70%、源端口70%作为初始扩容预警线，压测后调整。
- Prometheus按节点/服务聚合，避免每个源IP或连接ID成为永久标签。TCP_INFO保持有界抽样。

上线前验收清单
独立环境用10000真实认证身份，分别跑1/5/10连接；逐步增加吞吐、上下行混合、空闲与重连，
覆盖至少1小时持续传输与高连接周转。记录CPU、RSS/内核socket内存、GC、FD、TIME_WAIT、
conntrack、源端口余量、拨号/首包p95/p99、吞吐、公平性和计量误差。
测试单组故障时的新连接接管与配额一致性；达标后分批迁移新连接，保留旧连接自然排空。
现有服务器没有执行这种万人生产流量压测，也没有自动采购/新增服务器。
